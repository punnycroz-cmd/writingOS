# Phase 3B SourceFactLedger Specification

## Purpose
The SourceFactLedger provides a structured, formal mapping from the Nonfiction discovery corpus (`claim-inventory`) and verified evidence (`source-verification-ledger`) to actual facts. It serves as the canonical epistemic boundary, explicitly separating unverified candidates from proven ground truth.

## Schema Definition
The ledger consists of an array of objects matching the `SourceFactLedgerRecord` schema:

* `ledgerFactId`: Unique ID (e.g., LGR-NF-0001).
* `claimId`: Reference to the original candidate claim.
* `sourcePackSourceId`: Reference to the original source.
* `claimText`, `claimType`, `epistemicStrength`, `causalStatus`: Inherited directly from the discovery corpus.
* `sourceVerificationStatus`: Inherited directly from the source verification ledger (e.g., VERIFIED, BLOCKED, PARTIALLY_VERIFIED).
* `factVerificationState`: The epistemic state of this specific factual claim. Valid states are `CANDIDATE`, `UNSUPPORTED`, `PARTIALLY_SUPPORTED`, and `SOURCE_VERIFIED`.
* `evidenceType`: Characterizes the evidence available (`DIRECT`, `PARTIAL`, `BLOCKED`, `NONE`).
* `evidenceExcerpt`: Text snippet supporting the claim.
* `evidenceLocations`, `retrievedArtifact`, `publicationDateObserved`, `publisherObserved`, `authorObserved`: Provenance fields mapping to the verification ledger.
* `notes`: Operational or review notes.

## Epistemic Promotion Rules & Immutability Boundaries
1. **No Automatic Promotion**: A discovery claim cannot automatically become `SOURCE_VERIFIED`. In Phase 3B, all claims initialize as `CANDIDATE` or `UNSUPPORTED`.
2. **Blocked Sources**: If a source is `BLOCKED` (e.g., bot-blocked, CAPTCHA), it cannot provide `DIRECT` evidence. Any claims against a `BLOCKED` source default to `UNSUPPORTED` state and `BLOCKED` evidence type.
3. **No Hallucinated Ground Truth**: The variables `containsGroundTruth` and `sourceVerifiedClaims` must remain `false` and `0` respectively until an explicit evidence evaluation logic actively verifies them against the text artifacts in a future phase.

## Validation Invariants
The validation layer (`src/phase3/source-fact-ledger-validator.ts`) enforces:
1. **No Orphan Claims**: Every claim in the `claim-inventory` must map to exactly one ledger record.
2. **No Orphan Sources**: Every source referenced by the ledger must exist in the verification ledger.
3. **Epistemic Safety**: No `BLOCKED` source can supply `DIRECT` evidence. No claim can be marked `SOURCE_VERIFIED` in this phase.
4. **Schema Strictness**: All required fields must be present.

## Determinism
The SourceFactLedger is deterministically generated by `scripts/phase3/build-source-fact-ledger.ts` reading from the frozen source/claim inventories and the verification ledger. Running it multiple times yields identical cryptographic hashes.
