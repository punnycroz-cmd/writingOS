# Hash Policy — Phase 2B.5 Forensic Snapshot

## Purpose

This document explains which files in the forensic inventory are excluded from
SHA256 hash verification, why they are excluded, and how the final git commit
still provides integrity for them.

## Two Layers of Integrity

### Layer 1: Git Commit Identity (ALWAYS applies)

Every file committed to the `research/phase2b-golden-corpus-v1-reconciled` branch
is protected by git's content-addressable object store. The commit SHA is a hash
of the tree, which is a hash of file blobs. Any byte-level modification changes
the commit SHA. This provides **complete integrity** for all committed bytes,
including files excluded from the forensic inventory's hash verification.

### Layer 2: Forensic Inventory SHA256 (additional, independent checksum)

The `file-inventory.json` records an independent SHA256 hash for each preserved
file. This is an **additional** forensic checksum layer, not a replacement for
git integrity. It exists so an auditor can verify file contents independently
of git's internal representation.

## Excluded from Hash Verification

The following files are excluded from Layer 2 (forensic SHA256 verification) but
NOT from Layer 1 (git commit integrity):

### Category A: Self-referential files (`SELF_EXCLUDED_FILES`)

These files describe the inventory itself. Including them would create a
circular dependency: changing the inventory changes their content, which changes
their hash, which changes the inventory.

| File | Reason |
|---|---|
| `forensic/phase2b-5/MANIFEST.json` | Metadata about the inventory — changing inventory changes this file |
| `forensic/phase2b-5/file-inventory.json` | The inventory itself — self-referential |

**Integrity guarantee:** Git commit identity. These files ARE committed and
protected by the commit SHA.

### Category B: Derived/regenerated artifacts (`HASH_EXCLUDED_FILES`)

These files are regenerated on each reconciler or test run. Their content is
deterministic (same inputs → same outputs) but verifying their hash would
require rebuilding the inventory AFTER every reconciler run, creating a fragile
ordering dependency.

| File | Reason |
|---|---|
| `writing-engine/logs-golden-v1/canonical-case-ledger.json` | Regenerated by reconciler |
| `writing-engine/logs-golden-v1/reconciliation-report.json` | Regenerated by reconciler |
| `writing-engine/logs-golden-v1/consistency-check.json` | Regenerated by reconciler |
| `writing-engine/logs-golden-v1/summary.json` | Regenerated by reconciler |
| `forensic/phase2b-5/test-results/reconciler-output.txt` | Regenerated by reconciler |
| `forensic/phase2b-5/test-results/corpus-tests.txt` | Regenerated by test runner |
| `forensic/phase2b-5/test-results/lint.txt` | Regenerated by linter |

**Integrity guarantee:** Git commit identity + cross-validation. The
`consistency-check.json` itself validates that the ledger, summary, and
reconciliation report are internally consistent (checks #1–#19). The test
outputs are verified by re-running the tests (67/67 pass).

## Files REMAINING Hash-Verified

All other preserved files (~943 files) have their SHA256 hash verified by check #20.
This includes:
- `corpus/golden-v1/cases.jsonl` (corpus ground truth)
- `corpus/golden-v1/corpus-manifest.json`
- `src/corpus/*.ts` (reconciler, classifier, parser, validator)
- `tests/corpus/*.test.ts` (all test files)
- `writing-engine/logs-golden-v1/results/GC-*.json` (per-case results)
- `docs/corpus/*.md` (documentation)
- `forensic/phase2b-5/working-process.md`, `timeline.md`, `commands.log`, etc.

Any tampering with these files would be detected by check #20 as a `HASH_MISMATCH`.

## Why This Is Acceptable

1. **Git integrity is the primary guarantee.** The commit SHA on the remote
   branch is the final authority. Any modification to ANY committed file
   (hash-excluded or not) changes the commit SHA.

2. **Derived artifacts are cross-validated.** The reconciler's own consistency
   checks (#1–#19) verify that the derived artifacts (ledger, summary,
   reconciliation-report) are internally consistent with the corpus and results.

3. **The hash-excluded set is small and well-defined.** Only 9 files out of
   ~952 are hash-excluded. The remaining ~943 files have full SHA256 verification.

4. **The exclusion is documented.** This file, `excluded-files.json`, and the
   `HASH_EXCLUDED_FILES` constant in `src/corpus/forensic-validator.ts` all
   explicitly list the excluded files and reasons.
